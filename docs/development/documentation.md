# Documentation policy

Apply this policy to code changes, documentation changes, and reviews. Update documentation in the same change as the behavior it describes.

## Placement

| Location               | Content                                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------------------ |
| Root readme files      | Project purpose, end user prerequisites, everyday actions, and links into `docs/`.               |
| `docs/README.md`       | Index of the canonical guides and decision records.                                              |
| `docs/usage/`          | Detailed instructions for site users.                                                            |
| `docs/development/`    | Contributor setup, architecture, content editing, testing, and CI.                               |
| `docs/adr/`            | Significant decisions, their context, alternatives, consequences, and dated supporting evidence. |
| Component readme files | Component purpose and links to its canonical guide.                                              |

Give each topic one canonical explanation. When moving a topic, update all references and remove the old copy; do not leave compatibility stubs.

## Current behavior

- Use current code, maintained configuration, and package scripts as the source of truth. Verify commands, paths, settings, defaults, and guarantees before documenting them.
- Describe supported behavior directly. Remove obsolete workflows, legacy aliases, migration narratives, and duplicate explanations from active guides and examples.
- Keep version requirements in their maintained manifests and link to them instead of copying release snapshots into prose.
- Write concise instructions with prerequisites, actions, expected results, and constraints that affect the reader. Keep work logs and historical verification results out of active guides.
- Keep examples and validation aligned with supported behavior. Preserve documented recovery and data-protection contracts when they still apply.

## Decision records

Keep significant decision history in ADRs. Preserve accepted records. When a decision changes, add a superseding ADR and link the records in both directions. Record the decision status and date, relevant context, alternatives, consequences, and dated evidence.

Link to ADRs from current guides when the rationale is useful. Historical evidence explains a decision; it does not establish that a check passes today.

## Generated GitHub documentation

`.github/actions/**/README.md` and `.github/workflows/**/README.md` are autogenerated and are exceptions to the component readme rule. Never hand-edit them.

Change the relevant action or workflow YAML and generator inputs, then use the repository's established generator when available. If the checkout provides no generator, report that limitation; do not invent a command, add a generation pipeline, or manually replace generated output.

## Validation

Before completing a change:

1. Compare affected instructions and examples with current implementation and configuration.
2. Run the available Markdown checks and verify local file links and heading anchors, including inbound references after moves.
3. Run focused behavior checks when implementation changes, following [getting started](getting-started.md). Documentation-only changes need documentation checks, not new behavior tests or a full application run.
4. Report the checks actually run, their results, and any unverified claims or limitations. Keep required checks distinct from completed checks.

Use the [documentation index](../README.md) to find related guides.
