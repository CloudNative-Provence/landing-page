# CI and deployment

## Application checks and deployment

[`pull-request-ci.yml`](../../.github/workflows/pull-request-ci.yml) runs for pull
requests targeting `main` and merge groups.
[`main-ci.yml`](../../.github/workflows/main-ci.yml) runs for pushes to `main` and tags.
Both call [`__shared-ci.yml`](../../.github/workflows/__shared-ci.yml), which delegates
to the pinned Hoverkraft workflows:

- The repository linter checks repository files, workflow and composite-action
  pins, and GitHub Actions code with CodeQL. It uses the same image as the local
  [Dockerfile](../../Dockerfile).
- Node.js CI runs application linting, CodeQL, dependency review on pull requests,
  build, and tests, using `application/` as its working directory and `dist` as its
  build artifact. Dependency installation disables lifecycle scripts.
- The reporting job runs even after failures and combines repository lint,
  test, and coverage reports. Test artifacts use the calling job's report group
  and require both JUnit and LCOV files. Fork and Dependabot pull requests retain
  job summaries and artifacts without attempting to post PR comments.

Application lint diagnostics remain in their job's annotations and summary.
The semantic pull-request workflow validates Conventional Commit titles with
read-only repository access. The shared workflow supplies the default commit
rules when the repository has no commitlint configuration.

After CI succeeds on the default branch, the main workflow deploys
`application/dist` to GitHub Pages. Its deployment job uses the `github-pages`
environment and the build artifact ID returned by CI.

For local commands, see [development setup](getting-started.md).

## Dependency maintenance

External actions and reusable workflows are pinned to release commits, with the
version in a comment. [Dependabot](../../.github/dependabot.yml) groups weekly
GitHub Actions updates; its Docker updates maintain the local linter image.
Review release notes, workflow permissions, inputs, outputs, and report formats
before accepting a major update. Keep the local linter image aligned with the
image used by the released reusable linter workflow.

The [CI migration decision](../adr/0004-shared-ci-and-local-validation.md) records
the adoption rationale and dated upstream evidence.

## Automated schedule updates

[`fetch-schedule.yml`](../../.github/workflows/fetch-schedule.yml) runs daily at
06:00 UTC and supports manual dispatch. It calls the local
[`fetch-schedule` action](../../.github/actions/fetch-schedule/action.yml), then
creates and merges an update pull request on `chore/update-schedule` through the
pinned shared action.
Only `application/src/domains/pages/program/content/schedule.ts` is included in
the automated commit. The action's existing rebase and administrator-merge
defaults remain in effect; changing branch-protection policy is a separate
repository administration decision.

Required repository configuration:

| Name                     | Kind     | Used for                         |
| ------------------------ | -------- | -------------------------------- |
| `CONFERENCEHALL_API_KEY` | Secret   | Conference Hall schedule access. |
| `CI_BOT_APP_CLIENT_ID`   | Variable | GitHub App authentication.       |
| `CI_BOT_APP_PRIVATE_KEY` | Secret   | GitHub App authentication.       |

The workflow requests repository contents and pull-request write permissions for
the App token. This token lets generated pull requests run CI and their merges
trigger deployment. Local imports instead read `CONFERENCE_HALL_API_KEY`; see the
[import guide](program.md#import-the-schedule).
