# CI and deployment

## Application checks and deployment

[`pull-request-ci.yml`](../../.github/workflows/pull-request-ci.yml) runs for pull
requests targeting `main` and merge groups.
[`main-ci.yml`](../../.github/workflows/main-ci.yml) runs for pushes to `main` and tags.
Both call [`__shared-ci.yml`](../../.github/workflows/__shared-ci.yml), which delegates
to the pinned Node.js CI workflow with `application/` as its working directory and
`dist` as its build artifact.

After CI succeeds on the default branch, the main workflow deploys
`application/dist` to GitHub Pages. Its deployment job uses the `github-pages`
environment and the build artifact ID returned by CI.

For local commands, see [development setup](getting-started.md).

## Automated schedule updates

[`fetch-schedule.yml`](../../.github/workflows/fetch-schedule.yml) runs daily at
06:00 UTC and supports manual dispatch. It calls the local
[`fetch-schedule` action](../../.github/actions/fetch-schedule/action.yml), then
creates and merges an update pull request on `chore/update-schedule` through the
pinned shared action.

Required repository configuration:

| Name                     | Kind     | Used for                         |
| ------------------------ | -------- | -------------------------------- |
| `CONFERENCEHALL_API_KEY` | Secret   | Conference Hall schedule access. |
| `CI_BOT_APP_CLIENT_ID`   | Variable | GitHub App authentication.       |
| `CI_BOT_APP_PRIVATE_KEY` | Secret   | GitHub App authentication.       |

The workflow requests repository contents and pull-request write permissions for
the App token. This token lets generated pull requests run CI and their merges
trigger deployment. Local imports instead read `CONFERENCE_HALL_API_KEY`; see the
[import guide](program.md#import-the-schedule).
